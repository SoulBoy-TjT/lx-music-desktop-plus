# 完整 FLAC 因末帧后尾随数据被严格校验拒绝

## 关联文档

- 需求：[REQ-20260811-01 下载音频真实格式校验与降级发布](../requirements/REQ-20260811-01-download-actual-format-publication.md)
- 业务决策：[BIZ-20260811-04 完整 FLAC 仅对末帧后有界尾随数据执行无损规范化](../decisions/BIZ-20260811-04-flac-trailing-data-normalization.md)
- 技术方案：[DEV-20260811-01 下载真实格式校验与元数据发布技术方案](../designs/DEV-20260811-01-download-actual-format-publication.md)
- 当日进度：[PROG-20260811](../progress/PROG-20260811.md)

## 现象

用户安装并实际下载后，任务已经能够离开 `0%` 并到达 `99.99%`，但在最终校验阶段显示“下载内容不是可识别且可完整解码的 MP3、FLAC、WAV 或 APE”。详情中的 FFmpeg 错误为 `invalid sync code`、`invalid frame header` 和 `Invalid data found when processing input`，真实 FLAC 因而不能发布。

## 诊断证据

- 失败样例的 FLAC 音频主体均能解码到 STREAMINFO 声明的全部样本；例如《STRANGE》声明和实际解码均为 `9,903,158` 个样本。
- 最终合法音频帧的结构与 CRC 有效，但其结束位置之后仍有无法构成合法 FLAC 帧或元数据块的数据；《STRANGE》为 30 字节，另一固定样例为 15 字节。
- FFmpeg 在完整音频样本已经解码后才把尾随字节当作下一音频帧解析并报错，因此该错误不等同于中段音频帧损坏或下载缺失。
- 下载文件长度与来源响应一致，当前证据不支持客户端漏写、断点重复拼接或提前结束下载。

## 根因

REQ-20260811-01 新增的严格完整解码校验会正确拒绝任何 FFmpeg 解码错误，但当前实现没有区分“音频主体损坏”和“全部合法音频帧之后存在少量尾随数据”。因此即使全部声明样本和最终帧 CRC 都完整，尾随字节仍使整个文件被归入损坏内容并阻断发布。

## 期望修复与安全边界

- 先证明 FLAC 容器、全部声明样本、最终音频帧和 CRC 完整，再精确定位最终帧后的尾随范围。
- 只对满足 `BIZ-20260811-04` 且处于明确小范围上限内的尾随数据生成无损规范化候选；不得修改任何音频帧或依据播放时长猜测截断点。
- 对规范化结果重新执行严格完整解码、格式及样本数校验；全部通过才继续元数据写入和不覆盖发布。
- 中段损坏、样本不足或超出、CRC 错误、最终帧不可定位或尾随超限继续失败。

## 修复与验证证据

- 已实现 FLAC STREAMINFO、音频帧边界和 CRC 解析；只有声明样本全部解码、最终音频帧有效且异常数据全部位于末帧后的有界候选，才会生成无损规范化副本。
- 规范化只删除精确定位的尾随范围，不重编码或修改音频帧；随后重新执行严格完整解码、真实格式和样本数复验，任一步失败均不发布成品。中段损坏、样本数异常、CRC 错误、末帧不可定位和尾随超限继续拒绝。
- 尾随数据最终定向回归 3 个文件、75 项全部通过；最终全专题 55 个文件通过、1 个文件跳过，461 项通过、1 项跳过。
- 使用真实《STRANGE》文件经 Main public service 隔离验证：来源文件保持不变，规范化副本精确删除末帧后的 30 字节，严格复验通过。该验证不等同于安装态重新下载。
- Windows x64 NSIS 已重新构建，最终 `app.asar` 静态确认包含尾随数据规范化实现；安装包结构、随包 FFmpeg 和原生模块核验通过。

缺陷状态收口为 `fixed`。用户尚未运行本轮安装器并在真实 Electron 中重新下载《STRANGE》核对最终文件、元数据、封面和时长，因此不标记为 `verified`。
