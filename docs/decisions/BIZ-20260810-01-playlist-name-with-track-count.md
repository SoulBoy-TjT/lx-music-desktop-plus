## 决策问题

现有四个来源歌单只在名称中表达输入歌手名和平台，用户必须进入歌单才能知道实际收录曲数。名称需要直接携带本次最终写入的歌曲数量，并确保预览、同名检查、实际创建和失败残留报告不会使用不同名称或不同计数口径。

## 决策

### 1. 数量使用来源最终实际计划写入曲数

每个来源的数量 `N` 是该来源全部合法专辑按稳定 `track.id` 完成来源内去重后，最终提交给本地歌单写入接口的歌曲数组长度。

- Provider 声明曲数、去重前曲数、无效歌曲和其他来源歌曲均不计入 `N`。
- 名称中的 `N` 必须等于该歌单实际提交歌曲数；不得使用来源声明数、页面旧缓存或估算值。
- 任一来源最终为 `0` 首仍阻断整批创建，不生成带“`0首`”的歌单。

### 2. 名称采用无空格固定格式

四个目标名称固定为：

| 来源 ID | 歌单名称 |
| --- | --- |
| `kg` | `<输入歌手名>-酷狗-<N>首` |
| `tx` | `<输入歌手名>-qq-<N>首` |
| `wy` | `<输入歌手名>-网易-<N>首` |
| `kw` | `<输入歌手名>-酷我-<N>首` |

输入歌手名继续使用去除首尾空白后的共同查询词。分隔符两侧不增加空格，平台文案大小写严格保持为“酷狗”“qq”“网易”“酷我”。例如酷狗最终提交 77 首时，名称为“`薛之谦-酷狗-77首`”。

### 3. 所有目标名称使用同一规则

目标名称必须由同一命名规则基于 `{ inputArtistName, source, N }` 生成，并贯穿以下位置：

- 四来源目标名称预览。
- 既有本地歌单同名检查与冲突提示。
- core 实际创建歌单时传入的名称。
- 补偿失败残留报告。

core apply 必须以写入前重新组装并去重后的实际提交数组计算 `N`，不能只信任 UI 传入的名称或数量。若计划已失效或实际提交数组为空，沿用现有批次校验阻断，不创建部分来源歌单。

### 4. 其他写入规则不变

同名仍只提示，用户确认后创建新 ID，不覆盖或合并旧歌单；四歌单仍按全有或全无目标执行尽力补偿，普通本地歌单及原生下载语义不变。

## 对既有决策的修订

## 被比较的替代方案

### 方案 A：使用去重前或 Provider 声明歌曲数

不采用。该数量可能包含重复、无效或实际未提交的歌曲，名称会与歌单内容不一致。

### 方案 B：只在创建成功后重命名

不采用。同名检查和创建确认会使用旧名称，失败残留也无法稳定定位同一个目标。

## 确认项

- [x] `N` 为每来源最终去重后实际提交歌曲数。
- [x] 名称严格使用无空格格式“`<输入歌手名>-<酷狗|qq|网易|酷我>-<N>首`”。
- [x] 目标名称预览、同名检查、core 创建和补偿失败残留报告使用同一名称。
- [x] 名称中的数字必须等于该歌单实际提交歌曲数。
- [x] 0 首来源继续阻断整批创建。

## 实现与验证记录

- `createArtistDiscographyPlaylistNames` 集中维护四个平台文案和无空格名称格式，按去除首尾空白后的歌手输入及各来源最终曲数生成名称。
- batch apply 先用 `prepareArtistDiscographyApply` 取得每来源最终提交数组及 `plannedTrackCounts`，校验其长度与计划的 `deduplicatedTrackCount` 一致后，再以实际准备数组长度生成 core 创建名称；0 首和计数漂移继续在写入前阻断。
- Tools 的目标名称预览和同名检查复用同一 helper；core 补偿失败残留直接携带实际创建目标的同一名称。
- `npm run test:artist-discography`：37 个测试文件、234 项测试全部通过，覆盖四来源名称、输入 trim、去重后计数、计数漂移阻断、目标预览/同名检查与残留名称合同。
- Renderer TypeScript、core batch + test + Tools 定向 ESLint 和 `npm run build:renderer` 均通过；运行时代码中旧无数量命名无残留，相关文档无尾随空白。
- 最终独立交叉审查未发现 P0/P1/P2 问题。

真实 Electron 中的目标名称视觉展示及同名提示人工点击尚未执行；该边界不改变本业务决策的 `accepted` 状态，但继续约束 REQ 的整体人工验收。
