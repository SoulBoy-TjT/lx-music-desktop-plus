## 决策问题

原专辑抓取按一次一个来源设计，只能生成一个“`<歌手名> - 全专辑`”歌单。扩展到四个平台后，需要固定共同输入、来源身份确认、快照边界、并行与重试、跨路由会话保留、部分结果、歌单命名、同名处理及四次非事务写入失败时的用户可见语义。

## 决策

### 1. 一次只输入一个歌手名称

四平台批次入口只引导并接受歌手名称。系统去除首尾空白后保存为本批次的 `inputArtistName`，不再要求用户选择来源或为四个平台分别输入 ID、链接。

该名称只是四次来源内解析的共同查询条件，不代表跨平台唯一身份。

### 2. 四个平台各自完全匹配并统一确认

固定来源为 `kg`、`tx`、`wy`、`kw`。每个平台独立搜索名称完全匹配候选；多个完全同名结果按 Provider 稳定顺序使用首项。

系统在一个确认界面中同时展示四个平台的来源、头像、名称、来源内 ID 和可用的声明专辑数。四个平台均解析成功且用户统一确认后，才开始专辑抓取。不得把任一平台的歌手 ID 复用到其他平台。

### 3. 四份快照独立，不做跨来源合并

每个平台分别形成目录快照，并继续使用来源内专辑 ID、专辑详情和稳定歌曲 ID 进行归属、完整性校验及去重。

- 不跨来源合并歌手、专辑或歌曲。
- 不因名称、日期或曲目相似而选择所谓“最佳版本”。
- 每个平台保留独立专辑选择，写入时只使用该来源当前选中专辑。
- 一个来源的成功不得掩盖另一个来源的异常。

### 4. 抓取并行，取消和重试覆盖整批

四个平台可以并行解析和抓取，各 adapter 继续独立限制分页、详情并发和有限重试。

- 用户取消时，共享取消信号传递到四个平台；所有来源停止创建新请求。
- 用户重试时，丢弃四份旧快照并重新执行整个批次，不混合不同抓取时间的响应。
- 首期不提供单来源或单专辑增量重试。

### 4.1. 已完成快照在当前会话跨路由保留

抓取完成并形成预览后，普通路由切换不视为取消或重试。用户离开“专辑抓取”页面再返回时，继续使用同一页面会话，保留输入名称、同一 `batchId`、四份快照、专辑选择、逐来源 `partial` 授权和 apply 结果。

- 返回页面不得自动请求任何 Provider。
- 只有用户显式重新获取时才创建新批次并替换当前状态。
- 该状态只在当前应用会话内保留，不写入磁盘或数据库；刷新或重启后清空。
- 本规则只保留抓取已经完成后的快照；若切页时仍在身份确认或抓取中，页面失活会整批取消当前 planning，停止后续 Provider 请求，不在后台继续未完成抓取。

### 5. 部分结果按来源接受，阻断状态按整批生效

`partial` 可由用户按来源逐一明确接受。任何一个 `partial` 未被接受时，整批创建保持禁用。

任一来源为 `failed`、`cancelled`，或其选中专辑最终没有歌曲时，整批创建保持禁用。系统不得只创建其余来源歌单并把结果提示为本次目标已完成。

### 6. 固定使用输入名称、平台和最终歌曲数

四个目标歌单名称固定为：

| 来源 ID | 歌单名称 |
| --- | --- |
| `kg` | `<inputArtistName>-酷狗-<N>首` |
| `tx` | `<inputArtistName>-qq-<N>首` |
| `wy` | `<inputArtistName>-网易-<N>首` |
| `kw` | `<inputArtistName>-酷我-<N>首` |

名称使用去除首尾空白后的用户输入，不使用四个平台可能不同的规范化歌手名。`N` 为对应来源最终去重后实际提交歌曲数；名称不含分隔空格，且预览、同名检查、实际创建和残留报告必须使用同一名称。

### 7. 同名只提示，确认后仍新建

任一目标名称已经存在时，系统在写入前统一列出冲突名称。用户取消则不写入；用户确认则仍以新的唯一歌单 ID 创建四个同名歌单。

- 不覆盖、清空或合并既有歌单。
- 不将本次新歌加入既有同名歌单。
- 回滚只允许删除本批次生成的歌单 ID。

### 8. 四歌单采用全有或全无的尽力补偿

本地歌单创建和加歌不是数据库事务。系统仍以“四个全部成功或本次失败后全部撤销”为目标：

1. 写入前一次性验证四份快照、部分结果接受状态、专辑选择和目标名称。
2. 为四个新歌单预生成唯一 ID，并记录本批次边界。
3. 任一创建或加歌失败时，删除本批次已创建的全部新歌单。
4. 全部补偿成功时返回批量失败且不留新增歌单。
5. 任一补偿失败时仍返回失败，并明确列出残留歌单名称和 ID 供人工处理。

不得为了实现表面上的全有或全无而删除批次开始前存在的用户歌单。

### 9. 继续生成普通本地歌单

四个结果均为普通洛雪本地歌单，不设置平台在线歌单的 `sourceListId`。创建成功后不自动下载，用户继续从各歌单进入洛雪原生批量下载流程。

- 本决策局部修订 `BIZ-20260809-02` 的专辑抓取输入：名称完全匹配继续有效，但四平台批次不再显示来源选择，也不以数字 ID 或官方链接作为该入口的兼容输入。
- `REQ-20260805-01` 的酷狗首期范围和历史验收证据不被改写；四平台交付由 `REQ-20260809-01` 独立验收。

## 被比较的替代方案

### 方案 A：用户逐个平台选择并重复抓取

不采用。它不能满足一次输入、统一确认、统一预览和一次批量创建的目标。

### 方案 B：把四个平台合并成一个歌单

不采用。不同平台的身份、专辑版本和歌曲 ID 不可直接比较，也不符合用户要求的四个来源歌单。

### 方案 C：一个来源失败时仍创建其余歌单

不采用。用户明确要求一次创建四个歌单；部分创建会让一次操作产生难以判断的完成状态。来源 `partial` 可以明确接受，但 `failed`、`cancelled` 和无歌曲继续阻断整批。

### 方案 D：同名时自动覆盖或合并

不采用。既有同名歌单可能包含用户修改，自动覆盖或合并会破坏用户数据。提示后新建可以保留既有内容和本次四歌单对称性。

### 方案 E：用数据库事务保证绝对原子

不采用。现有本地歌单通过多次 action 持久化，本需求不引入数据库迁移或重写歌单存储；采用批次 ID 边界和尽力补偿，并诚实报告回滚残留。
