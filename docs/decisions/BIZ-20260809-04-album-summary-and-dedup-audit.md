## 决策问题

四来源抓取仍需在内部穷尽专辑及详情，但逐专辑列表和选择会让用户承担不必要的目录筛选工作；与此同时，现有重复提示只给出数量或通用异常，无法说明具体保留了哪条、移除了哪条。预览需要改为来源级摘要，同时为实际发生的来源内去重提供足够的人工核查证据。

## 决策

### 1. 来源卡只展示来源摘要

每个来源卡展示歌手身份、抓取状态、合法专辑数、最终歌曲数、完整性和来源级异常说明。来源卡不展示或提供逐专辑明细，不列出专辑名称、ID、逐专辑状态或逐专辑问题，也不提供专辑勾选、全选、全不选等选择操作。

adapter 和核心仍须取得完整专辑列表及逐专辑详情；隐藏明细只改变用户界面，不降低抓取完整性要求。

### 2. 自动使用该来源全部合法专辑

批量写入时，每个来源自动使用该目录快照中的全部合法专辑及其合法歌曲。用户不能通过预览排除某张合法专辑；任一来源最终没有合法歌曲时继续阻断整批创建。

逐专辑请求、映射或归属校验异常必须聚合为该来源的完整性说明，并按既有规则将来源判定为 `partial` 或 `failed`。不得因为界面不展示专辑行而静默忽略异常；`partial` 仍须由用户按来源明确接受。

### 3. 最终歌单去重提供结构化核查信息

每个来源在汇总全部合法专辑的歌曲时，按该 Provider 的稳定 `track.id` 去重并保留首次出现项。只要实际移除重复歌曲，界面就为该来源展示结构化去重核查卡；没有去重时不显示该卡或空占位。

每组核查信息至少包含：

- 去重键，即稳定 `track.id`。
- 歌曲名称、Provider song ID 和歌手。
- 保留项与移除项各自所属的专辑名称和专辑 ID。
- 保留项与移除项各自的曲序及本次稳定遍历位置。
- “首次出现项保留”的明确原因。
- 可由用户复制的结构化信息。

该核查信息只解释来源内去重，不改变去重结果，也不在四个平台之间比较或折叠歌曲。

### 4. 早期重复单独提供核查卡

Provider 分页或专辑详情内部若在最终歌单汇总前已经识别并移除重复专辑或重复歌曲，必须另列来源内早期去重核查卡，不得仅把它混入最终歌单去重数量。

早期核查卡以 adapter 已保留的 `duplicate_album/duplicate_track` issue 标识符和最终保留快照为依据，展示阶段、对象类型、去重键及当前仍可核验的名称、Provider ID、专辑名称/ID 或位置。由于早期被移除原始副本已不可恢复，这类卡必须明确标记为非精确（`exact: false`）且说明信息受限；不可得字段允许省略，禁止将保留项字段复制成被移除项原始事实，或通过反推、拼接伪造。

### 5. 去重核查与页面会话一并保留

抓取完成后，来源摘要、来源级完整性说明、最终歌单去重核查和早期去重核查与同一 `batchId` 一并在当前应用会话内跨路由保留。返回页面不自动请求 Provider；只有显式重新获取才替换批次，刷新或重启仍不恢复抓取快照。

## 被比较的替代方案

### 方案 A：继续展示逐专辑列表但默认全选

不采用。即使默认全选，用户仍会被引导逐张审阅或修改目录，与本次只核对来源级结果的目标不符。

### 方案 B：只显示去重数量

不采用。数量无法证明具体保留和移除了哪些记录，也不能支持人工判断 Provider 数据是否异常。

### 方案 C：为缺失的早期字段推断完整记录

不采用。推断值会把不确定信息伪装成 Provider 原始事实；核查卡只展示去重发生时真实可得的数据。

### 方案 D：跨来源使用名称或 ID 去重

不采用。不同 Provider 的身份和 ID 命名空间互不等价，四个来源歌单必须继续独立。
