## 决策问题

现有四平台预览要求用户为每个 `partial` 来源额外确认“不完整结果也接受”，并在 batch apply 中传入 `allowIncompleteBySource`。该步骤与用户最终点击“四歌单批量创建”的明确意图重复，也增加了跨路由授权状态和写入预检分支。

现有去重核查同时展示去重键、Provider song ID、双方快照位置、首次出现原因等信息。重复标识符和内部遍历位置增加阅读负担，用户实际需要的是确认哪个平台发生了哪类去重、是哪首歌，以及保留和移除项分别来自哪张专辑。

## 决策

### 1. `partial` 非空即可直接参与批量创建

`partial` 继续表示来源快照存在缺失或异常，来源摘要仍必须展示完整性说明；但只要该来源最终形成至少一首合法歌曲，就与非空 `complete` 一样直接满足来源级写入条件，不再要求用户逐来源确认接受不完整结果。

- `complete` 且合法歌曲数大于 0：允许写入。
- `partial` 且合法歌曲数大于 0：允许写入，不显示额外接受控件。
- `failed`、`cancelled` 或合法歌曲数为 0：继续阻断整批创建。
- 一个来源被阻断时仍不得只创建其余三个歌单；四歌单全有或全无及尽力补偿规则不变。

用户点击一次“新建四个歌单”已构成对当前四份来源摘要和完整性说明的批量创建确认，不再叠加第二层 `partial` 授权。

### 2. 删除 partial consent 状态与 apply 输入

UI 不再维护、展示或跨路由缓存逐来源 partial consent。四来源 batch apply 不再接收 `allowIncompleteBySource`，也不保存 `acceptedPartialSources` 或等价状态。

`canApply` 与 apply 写入前复核使用同一组客观条件：四个来源均为 `complete/partial`、均有合法歌手和合法专辑，且最终去重后的合法歌曲集合非空；任一 `failed/cancelled/0 首` 立即阻断。

该修订不改变目录快照、来源状态、完整 issues、同名提示、四歌单固定命名、确定性写入或补偿语义。

### 3. 去重核查只展示人工判断所需字段

发生来源内去重时，每条核查信息只要求展示：

- 平台。
- 去重类型，例如最终歌曲去重、Provider 早期歌曲去重或 Provider 早期专辑去重。
- 歌曲名称与歌手；对象为专辑且没有歌曲语义时保持为空，不伪造。
- 一个可用标识符：优先展示稳定 `track.id`，没有稳定 ID 时回退为 Provider ID；不得同时重复展示等价的去重键和 Provider song ID，也不得在保留/移除两侧重复同一个 Provider ID。
- 保留项与移除项各自的专辑名称、albumId 和曲序；早期 issue 没有某字段时明确缺失，不从保留快照反推被移除项。

不再展示或复制专辑位置、歌曲位置、全局稳定遍历位置等快照位置。内部仍可保留位置数据用于确定性首次出现去重和测试，但这些内部字段不进入用户核查卡或复制文本。

首次出现项仍是实际去重算法的保留规则，但不再单独显示“首次出现保留原因”字段。复制操作如继续提供，只复制上述精简后的可见结构，不附加隐藏位置或重复 Provider ID。

### 4. 早期重复继续诚实表达信息边界

Provider/专辑内早期 duplicate 仍与最终 assembly 去重区分类型。早期被移除原始副本已经不可恢复时，继续标记 `exact: false` 或等价的非精确说明；只展示 issue 和保留快照中真实可得的字段，不能为了补齐精简卡而伪造歌曲、歌手、专辑、ID 或曲序。

四个平台之间继续不去重；无实际去重时不展示核查卡。

### 5. 跨路由只保留仍有业务意义的状态

抓取完成后跨路由继续保留输入、同一 `batchId`、四份来源摘要、完整性说明、去重核查和 apply 结果。partial consent 已被删除，因此不再属于页面状态、重新获取清理对象或路由持久化验收内容。

## 被比较的替代方案

### 方案 A：保留 partial consent 但默认勾选

不采用。默认勾选仍保留了没有独立业务价值的 UI 状态、路由缓存和 apply 分支，也不能比最终批量创建操作提供更明确的用户意图。

### 方案 B：`partial` 一律阻断

不采用。只要来源仍有合法歌曲，完整性说明已经能够表达缺失边界；一律阻断会让单张专辑异常导致四个来源都无法生成。

### 方案 C：只显示去重数量

不采用。数量不能说明保留与移除项来自哪张专辑；保留精简后的专辑归属和曲序可以支持人工判断，同时避免展示内部遍历细节。
